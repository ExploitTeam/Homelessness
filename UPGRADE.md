# Обновление MAX-бота: фонды, роли и история заявок

## Что реализовано

- 4 роли: `0` — обычный пользователь, `1` — менеджер пункта,
  `2` — администратор всего бота, `3` — администратор конкретного фонда.
- Создание фондов с названием и описанием, назначение администратора фонда по MAX ID,
  смена названия и описания. Глобальный администратор может перенести пункт в другой фонд.
- У фонда может быть любое количество пунктов. Администратор фонда работает **только**
  с пунктами собственного фонда. Глобальный администратор видит все фонды.
- Связь менеджеров и пунктов «многие ко многим»; меню назначения/снятия менеджеров
  находится в карточке пункта. Сотрудник без доступа к пункту не может подтверждать
  заявки даже по сохранённым старым кнопкам.
- Сообщение о новой заявке от существующего `/api/book` дублируется каждому остальному
  назначенному менеджеру. Это реализовано в клиенте бота **без изменения API**.
- Автоматическое завершение, отмена пользователем и отклонение сотрудником сохраняются
  в `booking_history`; смены статусов фиксируются в `booking_events`.
- Разделы: **Мои бронирования → История**, **Управление бронированиями → Пункт → История**,
  **Управление бронированиями → Пункт → Поиск по MAX ID**. История постраничная.
- Удаление активной брони и возврат свободного места выполняются атомарно; при завершении
  подтверждённой брони свободное место также возвращается.
- Идентификаторы удалённых броней повторно не используются, поэтому новые записи не
  перезаписывают старую историю.

## Установка на старую базу

1. **Остановите приложение** и сделайте отдельную резервную копию `database.db`.
2. Замените исходники кодом из архива, сохранив вашу `.env` и рабочую БД.
   В архиве намеренно **нет** `database.db`, чтобы она не была случайно перезаписана.
   Для чистой установки создайте пустой файл `touch database.db`.
3. Проверьте `DB_NAME` в `.env` (по умолчанию — `database`).
4. Запустите `docker compose up -d --build` или `python main.py`.
5. При старте `initialize_database()` автоматически добавит новые таблицы/поля, создаст
   «Основной фонд», отнесёт к нему старые пункты, перенесёт назначения менеджеров и
   занесёт имеющиеся **активные** брони в историю. Миграция повторно безопасна.
6. Зайдите под аккаунтом из `MAX_ADMINS_ID`: `Главное меню → Фонды`. Создайте остальные
   фонды, назначьте администраторов и перенесите пункты.
7. Затем выдайте сотрудникам роль менеджера через `Управление пользователем → MAX ID`,
   и привяжите их к одному или нескольким пунктам через `Управление пунктами`.

Важно: **уже удалённые до обновления брони не восстановить**, если их нет в резервной
копии или сторонних журналах. Новые отмены/удаления сохраняются.

Старые роли `2` остаются глобальными администраторами. Старые менеджеры сохраняют
назначения; роль администратора фонда — новый код `3`.

## Что не изменено

Файлы `api/http_server.py`, каталог `Web/` (исходники и собранный мини‑сайт,
без скачанных npm-зависимостей `node_modules`),
`openapi.yaml` и `DATA-API.yaml` оставлены без изменений. Мини-приложение по-прежнему
показывает **первого менеджера** в существующем поле `manager_info`; бот показывает
**всех** менеджеров. Отображение всех менеджеров именно на сайте потребует отдельной
доработки API и интерфейса мини-приложения.

Периоды автоочистки продолжают задаваться `UNAPPROVED_TTL`, `APPROVED_TTL` и `CLEAN_EVERY`
(часы). Фонды не скрывают пункты от обычных посетителей: ближайшие пункты и карта
остаются общими для всех фондов.

## Проверка

```bash
python -m unittest discover -s tests -v
python -m compileall -q main.py database maxbot
```

Тесты работают на временной SQLite-БД и не меняют вашу рабочую базу.
Реальная интеграция с MAX (включая доставку сообщений и отображение кнопок) требует
токена и ручной проверки в мессенджере.

## Известные ограничения

- Пока API/сайт не меняются, мини-приложение отображает только одного менеджера; всем
  назначенным менеджерам оповещения о создании брони отправляются в самом боте.
- Текущие `/api/book` и учёт `available_beds` сохранились без правок. Защиту от
  одновременного бронирования последнего места несколькими запросами желательно позже
  перенести в атомарную транзакцию вместе с созданием брони в API.
- История фиксирует изменения с момента установки версии; ранее физически удалённые
  записи восстановить нельзя.
