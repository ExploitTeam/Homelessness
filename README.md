# Хакатон по разработке бота для Макс.

## 1. Назначение решения. 

### Мы разработали бота, который **поможет** людям найти и получить помощь в трудной жизненной ситуации.

За основу мы взяли благотворительный фонд **"Ночлежка"**, который предоставляет
бесплатные места для ночевки, обогрева в холодное время года, бесплатные
медикаменты и еду, а так же многое другое. <br>
При помощи созданного бота
пользователи могут найти **ближайшую** точку, посмотреть доступные места,
забронировать себе место и связаться с менеджером. **Для администраторов 
и менеджеров выдаются дополнительные права**, позволяющие создавать и 
редактировать пункты, принимать или отклонять бронь, редактировать пользователей.
---

## 2. Основной пользовательский сценарий
1. Пользователь нажимает кнопку **Начать** или пишет /start
2. При необходимости указывает номер телефона, чтобы в последствии с ним
мог связаться менеджер
3. Нажимает кнопку "Отправить геопозицию"
4. Получает список всех пунктов, отсортированных от ближайшего к самому дальнему.
Может использовать фильтры для получения конкретных типов пунктов помощи.
5. Открывает мини-приложение с картой и бронирует место в выбранном пункте. 
В мини приложении отображается полная карта со всеми пунктами и информацией о них,
к каждому можно проложить маршрут на метро.
6. Бот присылает информацию о брони
7. Менеджер или администратор подтверждает или отклоняет бронь в боте.
Менеджер так же получает уведомление о новой брони в чат.
8. Пользователь получает уведомление о изменении статуса бронирования.
9. Неподтвержденная бродь удаляется автоматически через заданый интервал,
   (по умолчанию - 3 часа)
подтвержденная - так же через заданный интервал (по умолчанию - 24 часа)

Все брони **пользователь** может увидеть в боте. Путь к ним: <br>
`Главное меню -> Мои бронирования.` <br>
**Для Сотрудников** есть дополнительные разделы:<br>
- `Редактирование пунктов (создание нового или редактирование существующего).`
- `Управление бронированиями (отклоение или подтверждение брони).`

## 3. Состав и архитектура
МАКС (чат бот + мини приложение):
-   main.py (один процесс)
    - long poll bot MAX
    - FastApi на 8000 порту
      - /api/auth
      - /api/places
      - /api/book
    - Фоновая очистка броней
- database.db

| Компонент          | Роль                                                       |
|--------------------|------------------------------------------------------------|
| maxbot/            | Сценарии чат-бота, клавиатуры, брони, пользователи, пункты |
| api/http_server.py | JWT - сессия мини-приложения, списки пунктов, бронь        |
| database/          | SQLite; классы User, Homestay, Booking                     |
| Web/dist           | Сборка мини-приложения (карта + бронь)                     |
| parser/            | Геокодинг адреса через Nominatim                           |
Мини-приложение не живет отдельно от бота, открывается из MAX, авторизация через 
init_data
---

## 4. Запуск локальных компонентов
```bash
nano .env
touch database.db
# если база в .env называется по-другому, заменить database.db на другое имя
docker compose up --build
```
Остановка:<br>
```bash
docker compose down
```
Повторн запуск без пересборки <br>
```bash
docker compose up -d
```

## 5. Необходимые параметры окружения
1. Рядом с docker-compose.yml должен лежать файл .env (в репозиторий не входит). 
Образец — .env.example
2. Минимально для запуска
    - `MAX_TOKEN` — токен бота, выданный для хакатона
    - `JWT_SECRET` — секрет подписи сессии мини-приложения, любая длинная случайная строка

## 9. Внешние сервисы и интеграции

| Сервис        | Где используется             | Можно ли поднять в Docker                                                       |
|---------------|------------------------------|---------------------------------------------------------------------------------|
| MAX Bot API   | чат, кнопки, мини-приложение | нет, платформа хакатона                                                         |
| Nominatim OSM | координаты по адресу пункта  | нет, публичный геокодер; при недоступности пункт сохраняется без точки на карте |
| OpenStreetMap | карта в мини-приложении      | Да                                                                              |

Облачные LLM и GraphHopper в решении не используются.

Расстояние между пользователем и пунктом считается локально (формула гаверсинуса по широте/долготе). Это оценка «по прямой», не длина пешеходного маршрута.

Для проверки основного сценария проверяющему нужен аккаунт MAX и токен бота из `.env` / первого слайда презентации.

## 10. Описание работы с данными

Хранилище — один файл SQLite `database.db` (имя может быть другим, задается в .env) в корне проекта (в контейнере монтируется томом).

Основные таблицы:

- `users` — пользователь MAX, роль (`0` обычный, `1` менеджер, `2` админ), телефон, привязка к пункту, время последней брони;
- `homestays` — пункт помощи: адрес, места, часы, тип, координаты, статус работы;
- `bookings` — бронь: пользователь, пункт, время, признак подтверждения.

Персональные и медицинские данные сторонних людей в выборку не закладывались. В базе только то, что пользователь сам прислал боту (id MAX, имя, телефон) и карточки пунктов, которые заводят сотрудники.

Тестовые и справочные адреса пунктов — модельные/открытые данные организаций помощи. Это не выгрузка из государственной ИС. Отдельной интеграции с «Госуслугами» нет.

## 11. Порядок работы с тестовыми данными

При первом запуске `initialize_database()` создаёт пустые таблицы. Готовых «секретных» логинов в SQL нет: пользователь появляется после `/start` в MAX.

Чтобы проверить бронь целиком:

1. Напишите боту `/start` с обычного аккаунта — появится пользователь с `user_type = 0`.
2. С аккаунта из `MAX_ADMINS_ID` откройте «Редактировать пользователя» и выдайте второму аккаунту роль менеджера, привяжите к пункту.
3. Создайте пункт: «Редактировать пункт помощи» → адрес, места, часы, тип.
4. С обычного аккаунта отправьте геолокацию и забронируйте место в мини-приложении.

Если пункты уже есть в приложенном `database.db` на стенде команды — можно сразу открывать карту. Для чистой проверки файл базы создайте пустым: `touch database.db`.

## 12. Пошаговый сценарий проверки
1. `nano .env` и заполните `MAX_TOKEN`, `JWT_SECRET`.
2. `touch database.db && docker compose up --build`.
3. Откройте http://127.0.0.1:8000 — должна открыться оболочка мини-приложения (без валидного `initData` API брони вернёт 401, это ожидаемо).
4. В MAX найдите бота по ссылке с первого слайда презентации, `/start`.
5. Отправьте геопозицию → список пунктов с пагинацией и фильтром типа.
6. Откройте мини-приложение из бота, выберите пункт, нажмите бронь.
7. `GET /api/places` с JWT после `/api/auth` возвращает пункты и вложенную бронь пользователя.
8. Менеджер в чате видит заявку, кнопки «Подтвердить» / «Отклонить».
9. Пользователь в «Мои бронирования» видит статус и может отменить бронь.

## 13. Примеры ожидаемого поведения системы
| Действие | Результат |
|---|---|
| `/start` | Приветствие, меню, кнопка геолокации |
| Геопозиция | Карточки пунктов, ближние выше |
| Фильтр типа | В списке только выбранные типы, на кнопке галочка |
| Бронь при `available_beds > 0` | `200`, мест становится на 1 меньше, сообщение пользователю и менеджеру |
| Повторная бронь того же пункта | `409` |
| Слишком частая бронь | `429` |
| Бронь без мест | `400` |
| Подтверждение менеджером | `is_approved = 1`, уведомление пользователю |
| Отмена / автоочистка | запись удалена, `available_beds += 1` |
| Нет `Authorization` на `/api/places` | `401` |

## 14. Известные ограничения
1. Nominatim иногда не находит точный номер дома; В таком случае по умолчанию ставится центр Москвы. Координаты можно задать вручную в разделе Редактирования пунктов.
2. Сортировка «ближайший» идёт по прямой, не по дорожной сети.
3. База данных **SQLite** – производительность при большом количестве запросов стремительно падает
4. Неподтверждённые брони живут `UNAPPROVED_TTL` часов, все брони — не дольше `APPROVED_TTL`.
5. Решение не заменяет соцработника и не является официальным сервисом ведомства.
